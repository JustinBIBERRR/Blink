# Fog notification implementation and validation

The scheduler submits one start event at fog prelude entry and one completion event at the 23-second natural end. The shared presentation adapter drains the queue before visiting monitor windows. Soft mode, disabled notifications, explicit close, pause, lock, sleep and Windows silence do not produce completion notifications. Interrupted rounds discard an unsubmitted prelude. Config files lacking the setting default to enabled; disabled state survives storage roundtrip. Delivery errors do not feed back into the scheduler.

Inspected local dependency source: tauri-plugin-notification 2.3.3 `desktop.rs` only calls `sound_name` when supplied; notify-rust 4.17.0 `windows.rs` maps missing sound to `None` and passes it to winrt-notification. The final WinRT wrapper source was unavailable locally, so absence of a sound parameter was not treated as evidence of silence. The fog path instead explicitly includes `<audio silent="true"/>`, supplies the configured installed application identifier, and initializes COM on its delivery thread. macOS uses UNUserNotificationCenter with `content.sound = nil`, requests alert authorization only, and its foreground presentation delegate requests banner/list without sound.

Validation on macOS: 48 Rust tests passed after merging eraser integration 43ba1f9, including controlled-time notification count/timing, soft/disabled modes, all interruption paths, stale queued prelude cancellation, and config storage compatibility. `npm run build` passed. Native Objective-C adapter compiles and links UserNotifications successfully. TDD red stages observed missing notification drain API, missing configuration field, and an interrupted round retaining its queued start, followed by passing implementations.

Not yet verified: installed Windows toast identity and banners; installed macOS permission prompt/banner behavior, denial and Focus/DND filtering, and audible silence on either machine. Automated tests prove submission policy, not OS display. Windows native adapter still requires the Windows build/CI and installed-app acceptance. macOS requires a bundled app identity; the adapter safely skips unbundled command-line runs.
